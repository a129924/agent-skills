# Examples

- Positive: Map a non-trivial behavior change into RED tests that cover happy path, error handling, boundary behavior, state effects, and integration points before implementation starts.
- Positive: Treat a trivial D1 outcome as a valid narrow-fit result and avoid forcing a heavyweight test-authoring flow.
- Negative: Continue as if the work were still test-first after production code already changed, or fabricate assertions for vague requirements instead of naming the ambiguity.
