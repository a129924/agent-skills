# 範例的證據角色
以下皆為設計與判讀示意，**未實際執行**，沒有實際執行日期、輸出或成功紀錄。示意結果只能說明如何判讀；正式紀錄必須換成實際環境、指令、資料及證據位置。未註明連續關係者為獨立情境，不共用實驗編號或臆造投入預算。

# UTF-8 跨多位元組區塊：有效的最小設計
- 輸入：使用者已給問題「候選增量解碼器能否保留跨區塊 UTF-8 字元？」與是否採用此解碼器的決策，未提供假設或判準。agent 先查官方文件／原始碼，若仍需執行，主動提出假設：有效 UTF-8 輸入在此次選定邊界切開後仍正確解碼。結果影響採用此解碼器或改用可保留未完成位元組的方案。
- 關鍵操作：以 `A你B` 的 UTF-8 位元組 `41 E4 BD A0 42` 為資料，分成 `[41 E4]`、`[BD]`、`[A0 42]`，按順序送入同一增量解碼器，再做 final flush；收集各次輸出與合併結果。這會把三位元組字元切在內部，能暴露跨批次狀態保存問題。
- agent 主動提出事前判準並在執行前固定，不要求使用者填判準：成功＝完整接收與 flush 後合併輸出恰為 `A你B`，無替代字元、漏字或例外；失敗＝環境及輸入有效但觀察到上述差異；無法判定＝候選 API 或必要環境不可用、未送完或輸出證據缺漏。
- 必要證據：實際解碼器版本、設定、呼叫順序／指令、每批位元組與輸出、flush 輸出及比較結果。依情境提出有限投入建議與停止條件，在既有授權內執行；不能確認的重大投入或授權界線才需澄清。
- 示意判讀：即使這組輸入成功，也僅支持該環境與選定切點；不能保證所有 Unicode、所有切點或非法 UTF-8 行為。

# 反例：整檔讀取不足以回答
同一問題只讀整份 `A你B` 檔案、一次解碼，或只跑 build／一般測試。它沒有跨批次保留不完整字元的操作，所以即使通過也不足以分類原假設為成功。主動指出缺少的分批輸入與觀察，保留現有證據但不冒稱完成；設計補足後才在授權範圍執行。

# 唯讀即可回答：不用實驗
- 輸入：需要確認目標版本某函式的預設參數，以決定呼叫時是否明傳參數。
- 依據：查看該版本官方文件與函式原始碼簽名；兩者一致且足以回答問題時，留下實際來源、版本、位置、事實與決策影響。
- 判讀：不建立 `experiments/E001/`，也不把「沒有跑實驗」當成證據不足。若來源版本或條件不符，先補唯讀資訊，再判斷是否必須執行。

# 假設否定，驗證任務仍可完成
- 輸入與事前判準：沿用跨區塊案例，且必要環境及資料有效。
- 示意結果：若實際分批輸入在首批未完成字元處拋錯，保存版本、呼叫與錯誤證據後，依原判準記「失敗」。這是示意，並非已觀察的輸出。
- 完成判斷：若實際證據足以排除此方案，本輪任務可記「是」，理由為已回答主要問題並支持排除；不必讓假設成立才結束。替代方案正式採用仍走原流程。

# 環境不足：無法判定與決策受阻
- 輸入：驗證指定版本依賴在目標平台的行為；判準事前要求該依賴可載入且必要設定有效。
- 示意結果：嘗試後依賴無法載入，沒有取得目標行為觀察。記「無法判定」，附實際嘗試指令、環境版本、載入失敗證據及未滿足前置條件，不能記假設「失敗」。完全未嘗試則記「未執行」。
- 完成判斷：清楚記錄原因、缺少可用依賴及目標觀察、決策仍不能選定方案，並說明需在可用環境補證據，可完成本輪紀錄；沒有這些內容則未完成。若下一動作依賴該結論，skill 處理標 `BLOCKED`，不因本輪結束而推進。

# 有限 simulated 條件：限制結論範圍
- 輸入：問題「固定兩段合法回應的模擬來源能否被候選消費者逐段處理？」；結果影響是否繼續評估該方案。以兩段已知可公開資料做模擬來源，收集段順序與合併輸出。
- 事前判準：成功＝兩段順序及合併內容皆相符；失敗＝前置條件有效但順序／內容不同；無法判定＝消費者未啟動或觀察缺漏。
- 必要證據：模擬設定、實際兩段輸入、操作指令及實際觀察，明標依賴為 simulated。
- 示意判讀：即使成功，也只支持該模擬兩段條件，不能推論真實服務延遲、錯誤、背壓或斷線行為。若原決策要求真實服務保證，這些證據不足，須標明缺口；不能偷偷改成較弱問題後宣稱原問題完成。

# 缺少判斷輸入：先指出缺口
- 輸入：「幫我試看看這個套件」；沒有主要問題、決策影響、判準或投入界線。
- 正確：先唯讀查已給資料與官方文件／原始碼；若仍不知道真實問題與實作決策，任意選擇會實質改變需求，詢問必要的問題／決策澄清，依賴動作為 `BLOCKED`，已有來源可保存為 `SOFT FAIL／INCOMPLETE`。問題與決策明確後，假設、操作、區辨輸入及技術判準由 agent 主動設計；投入可依情境提出有限建議，不要求使用者預先填齊技術欄位。
- 反例：自行假定「安裝成功就是可行」、杜撰三十分鐘預算、建立 E001 並執行。這沒有有效問題與判準，也沒有取得必要操作界線。

# 編號與歷史證據
建立前檢查目標專案既有 E001、E002 與歷史占用；選下一個未使用編號，不因目錄看似空白而覆寫既有紀錄。重用歷史證據時說明問題、環境、輸入及判準的適用性，引用原紀錄並保留原文；問題或判準改變時另立實驗，既有檔案修改仍須授權。


# 連續案例：OAuth 儲存 → refresh
以下 E001、E002 是同一組連續設計示意；編號須依目標專案實際占用調整，並非已執行的 OAuth 實驗。先查目標 OAuth 與儲存方案的文件／原始碼；只有依據不足且影響方案選擇時才進實驗。

## E001 完成後才發現 E002
- E001 問題：登入取得的目標 token，能否在指定環境寫入指定儲存方案，並在所需讀取情境讀回？事前固定 token 類型、環境、寫入／讀取操作及比較方式。成功＝指定資料在選定情境讀回一致；失敗＝前置條件有效但寫入或讀回不符合；無法判定＝必要環境、權限或觀察不足。
- E001 完成後才發現需要驗證 refresh，是允許的逐步發現。保留 E001 原問題、判準與結果，另立 E002；不把 refresh 補成 E001 已驗證的能力。
- E002 問題：目標 token 需要更新時，候選流程能否完成 refresh、寫回更新後的 token，並讓後續請求使用它？依目標協定與環境固定觸發方式及區辨輸入。成功＝觀察到 refresh、更新寫回及後續使用皆符合預定結果；失敗＝前置條件有效但任一必要行為不符；無法判定＝無法觸發更新、必要依賴不可得或證據缺漏。
- 反例：事後改寫 E001 的問題或判準，或因 E001 成功就標 E002 成功。能存取 token 並不證明 refresh 成立。

## 強依賴與程式重用
- E002 的「環境與前置條件」列明依賴 E001 的具體能力，例如指定環境與設定下的登入及 token 寫入／讀回；只引用 E001 真正取得的證據，未驗證能力仍列為依賴假設。記錄原紀錄位置、版本與適用條件，不能只寫「E001 成功」。
- E002 的「重現步驟」引用實際共用程式、設定版本及執行順序；「結果與證據」「結論與限制」另記 refresh 的實際觀察與限制。模擬依賴只支持相應模擬條件。
- 反例：引用前次結論卻省略環境差異，或以成功讀回舊 token 代替 refresh 與後續使用新 token 的觀察。

## 開始 E002 後才整理共用程式
- 可在既有授權內，將 E001 的必要登入或儲存邏輯抽離供 E002 使用。記錄抽離來源及前後版本、更新重現方式，保留 E001 原問題、判準、結果與證據，並保有可還原的原版本或其他可追溯依據；不覆寫成另一個實驗。
- 按影響判斷重驗範圍：例如改變儲存讀寫行為，需補驗 E001 受影響的操作；僅搬移位置且有依據確認行為未變，可檢查入口與引用是否仍可重現，不要求全面重跑歷史實驗。將判斷依據與證據適用限制寫入既有段落。
- 不必預先設計共用架構。實驗增多時，可按主題分組、拆分共用程式，或保留附來源版本的副本；不強制所有邏輯進入單一 `shared/`。以容易執行、證據可追溯與修改影響可掌握為尺度。
- 反例：抽離時刪掉原結果、持續修改共用邏輯卻沿用不再適用的證據；或每次搬檔都要求重跑所有歷史實驗。共用程式變大也不是自動移入正式來源區的理由或授權。

## 實驗入口不能授權正式核心流程
假設這個專案已明確將 `Sources/` 定位為預定供 production 使用的來源區：

```text
experiments/
  E001/
    README.md
    verify_token_storage.*
  E002/
    README.md
    verify_token_refresh.*
Sources/
  login/
    oauth_client.*
    token_store.*
    token_refresh.*
```

- 只有可行性驗證授權時，agent 卻自行在此建立正式登入、儲存及 refresh 核心流程，即已跨入正式實作；入口與紀錄留在 `experiments/` 不能提供此授權，也不必等到發布或接入產品才辨識。
- `Sources/` 僅為案例名稱。其他語言、框架或專案須依其規範與實際用途辨認正式來源區，不能僅憑 `Sources`、`src` 或檔案副檔名判定；若只是另一個實驗資料夾，也不能因名稱就判越界。
- 正例：只有驗證授權時，保留必要實驗程式並記錄採用建議，將正式採用交回原流程。實驗可讀取或呼叫既有正式程式，不能把此邊界擴成全面禁止。
- 正例：原任務已明確授權「實作並驗證」時，按原實作與審查流程完成正式整合，無須新增重複確認。驗證結果仍只支持其已測條件，不代替正式實作與審查。
- 反例：以「尚未發布」「只有入口在 experiments」「shared 太大」為由，自行新增或修改正式核心流程。
