# 選擇性採用示例

以下全為示意情境，檔名與結果不是實際執行證據。

## 一個實驗，三項能力
E001 成功驗證分批解碼 A、重試 B、示範介面 C。需求只要 A，正式程式已有 B。

- 選 A，抽取必要邏輯並調整到正式介面；保留跨區塊字元測試。
- B 沿用既有能力，不搬入實驗副本；C 無正式用途，排除。
- A 完成實際接入及對應行為驗證後才記已採用。B 的行為滿足與來源關係分開記，C 引用排除理由。
- 不以 E001 成功或 A 已完成，將 E001 的全部能力標成已採用。

## 跨實驗依賴
A 需要 E002 的識別能力 D，但不需要 E002 的 CLI 與輸出介面。查正式能力能否供應 D；有則沿用，無則只選 D 及其必要依賴。若 D 依賴的真實服務仍未證實，停止依賴它的實作，交代缺口；不能因 E002 使用 mock 通過而假設真實服務成立。

## 重寫與部分採用
驗證使用單檔同步程式，正式來源有既定生命週期與錯誤契約。只採其演算法規則並重寫；以原能力、來源版本、正式接入與行為測試串起追溯，不要求保留實驗函式或檔名。若只完成核心規則但尚未接上必要入口，記部分採用或依證據記不確定，列出未接入範圍；檔案存在不足以宣稱已採用。

## 授權與寫入限制
原任務是「實作並驗證 A」時，沿原流程完成，不再要求同範圍實作批准。原任務只有驗證 A 時，先給出具體採用方案及精確寫入範圍，不寫正式來源。不能寫入獨立採用紀錄時，交相同模板內容與限制，不將它塞進實驗 README。

## 舊資料與已存在能力
舊實驗沒有 tracker；正式程式已提供相同行為。根據行為、接入與驗證證據記能力已滿足；若缺少來源關係證據，明記來源關係不確定，不聲稱是從該實驗採用。本輪補建能力識別與觀察日期，不冒充當年的採用紀錄。尚無足夠查核時，不從缺 tracker 推論未採用。

## 假設失敗或無法判定
E003 否定方案 X，支持選擇既有方案 Y：保留 X 的失敗與原證據，評估 Y 所需的證據與需求，不把 X 程式移植。E004 尚無法判定真實依賴時，驗證任務即使已完成紀錄，受阻能力仍不能推進；採用進度不由實驗四狀態推導。

## 誤用訊號
「成功就全部搬入」「名字一樣就是已採用」「build 過就算接入」「為了紀錄方便改寫實驗結果」均不足以支持採用。回到所選能力、原授權、實際接入及對應行為證據檢查。
