# 選擇性採用示例

以下全為示意情境。檔名與結果僅用來說明判定方式。

## 一個實驗，三項能力

E001 成功驗證分批解碼 A、重試 B、示範介面 C。正式需求要新增 A，正式程式已有 B。抽取 A 的必要邏輯調整至正式介面，保留跨區塊字元測試。沿用 B 並記錄等效行為的證據及可查得的來源關係。C 無正式用途，記排除理由。A 的採用依實際接入及行為驗證判定。

## 跨實驗依賴

A 需要 E002 的識別能力 D。先查既有正式能力能否供應 D，必要時只選 D 及其必要依賴，排除無關的 CLI 和輸出介面。若正式交付須依賴尚未證實的真實服務，保留服務缺口並暫停依賴它的實作。使用 mock 所取得的結果限於已查驗的條件。

## 重寫與部分採用

驗證使用單檔同步程式，正式來源有既定生命週期與錯誤契約。採用演算法規則並重寫，以原驗證版本、正式接入與實際執行結果保持追溯，可沿用正式專案的檔名與函式設計。本輪承諾接上批次入口，若已證實核心規則落地且缺該入口，記部分採用並列剩餘項。無法確定落地情形時記不確定。

## 純契約與具體消費端

本輪採用一份事件資料契約。下游消費端用固定事件樣本查驗各必填欄位及版本規則，保留消費端版本、相容性結果與適用範圍。對本輪純契約交付，這些結果可以支持已採用。只有契約檔存在或沒有比對結果時，仍缺遵循證據。

## UI library 與凍結驗證

本輪交付正式 UI library 的表單元件及輸入驗證。舊驗證 Preview 已依專案規則凍結，改用獲准的受控 host，保留舊 Preview 版本及重現線索。在受控 host 直接載入正式元件並執行有效、無效輸入，記錄 host 與元件版本、fixture 用途及結果。必要元件行為驗收具足時可記已採用，完整 App 組裝在此輪範圍外。

## Pipeline 與持續維護的驗收工具

本輪交付清理後接正規化的 Pipeline 協調行為。既有 runner 是持續維護工具，原授權涵蓋必要改接。讓 runner 直接呼叫正式 Pipeline，用 fixture 供應輸入，查驗實際步驟順序、中間資料及輸出，記錄 runner 與 Pipeline 的版本。若來源規則禁止改接，先用獲准位置的替代入口。沒有可用位置時，提出最小改接差異及所需決定，保留可獨立完成的步驟與證據。

## Facade、依賴替身與產品整合

本輪交付正式 Facade 的請求轉送及錯誤轉譯。測試直接呼叫真實 Facade，以替身提供範圍外的外部服務。記錄 Facade 與測試入口版本、替身角色、實際行為及證據限制。只承諾 Facade 協調時，兩項行為皆通過可支持採用。若本輪還承諾產品整合，另取得實際產品入口呼叫該 Facade 的結果。若已查驗 Facade 協調而缺必要產品證據，整項交付記部分採用，保留已查驗行為並列出整合缺口。

若測試替換了 Facade 本身、正式方法為空，或只有未執行的測試或 Preview 宣告，協調行為仍缺驗收證據。

## 授權與寫入限制

原任務是「實作並驗證 A」時，沿原流程完成原授權範圍。原任務只有驗證 A 時，交付具體採用方案與精確寫入範圍。若只有採用紀錄無法寫入，交付相同模板內容及限制，保留實驗 README。曾有 Plan 觸及正式來源且已結案時，依專案現行規則和本輪授權判斷該來源能否改動，以 Git 歷史追溯原版本。

## 舊資料與已存在能力

舊實驗沒有 tracker，正式程式已提供相同行為。有實際接入與驗證證據時，記能力已滿足。實驗來源關係缺證時記不確定。本輪補建的能力識別須標記並附觀察日期。缺少 tracker 或新模板欄位本身不支持未採用判定。

## 假設失敗或無法判定

E003 否定方案 X，並有證據支持既有方案 Y。保留 X 的結果與原證據，按正式需求檢視採用 Y 的依據與限制。E004 尚無法判定真實依賴時，即使驗證任務已完成，仍暫停依賴該缺口的採用工作。
