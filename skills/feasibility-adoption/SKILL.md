# Purpose
將有證據支持、符合正式需求的驗證成果選擇性採用，留下能力／決策到正式實作的對應。驗證成功不表示已實作，也不表示整個實驗都應搬入。

# Trigger / When to use
- 使用：已有可行性證據，需要決定哪些能力進入正式實作，或執行已授權的選擇性採用。
- 排除：重新設計可行性實驗、無驗證成果的一般功能實作、全專案採用盤點、發布或改寫鎖定決策。
- 可從文件／原始碼驗證結論開始，不要求必須有實驗目錄或成功標記。

# Inputs
- 目標需求、原任務授權、已鎖定決策及目標專案規範。
- 選定驗證的問題、結論、來源版本、條件、限制與證據；實驗程式只是可選素材。
- 可得正式來源、實際接入點、既有能力及採用／決策紀錄。

# Process
1. **定位需求與授權。**唯讀確認要實現的行為、原決策及正式來源。`src-implementation` 是泛稱，依語言、框架、實際用途與專案規範定位，不只看目錄名。先查可得資訊；只有仍會實質改變需求、風險或授權的歧義才詢問並停止依賴動作。
2. **拆出必要能力。**以能力／決策辨識哪些成果支持目標需求，引用來源及適用條件，分開事實、推論與缺口。列出重用、抽取調整、重寫或排除的方案與理由；不因實驗成功選入整個目錄。模擬與有限輸入的證據不能外推，失敗／無法判定也不能支持未證實的採用假設；若已支持另一選擇，須明列其證據與限制。
3. **確認必要依賴。**對所選能力追到足以實作的依賴，每項對應既有正式能力、此次必要實作或尚未解除的缺口。依賴另一實驗不代表要搬入整個實驗；等效既有能力可滿足依賴，但不能無證據宣稱源自該實驗。阻擋依賴未解時保留方案，不推進依賴它的實作。
4. **形成具體採用方案。**列明選定與排除範圍、正式接入位置、必要調整及驗證方式。必要邏輯與有價值的測試可重用、調整或重寫；無正式用途的 harness、模擬依賴與示範入口排除。確認正式介面、錯誤處理、生命週期及適用條件，不將實驗架構當作正式架構。
5. **依原授權實現。**原任務已授權實作時，沿專案原實作、必要驗證與審查流程完成 bounded implementation，不重問相同授權。只有驗證授權或模式不允許寫入時，交付可審查的具體方案，不修改正式程式。影響鎖定決策交原變更流程；不自行重開。實際接入與行為證據不足時，不能將計畫或檔案存在標為已採用。
6. **獨立記錄。**沿用專案既有採用紀錄落點；沒有則預設 `docs/feasibility-adoption.md`。按既有寫入權限用[模板](templates/adoption-record.md)新增／更新，保留歷次依據，不寫回實驗 README。不能寫入時交相同結構內容與限制。追溯來源版本、能力、選定／排除、依賴、方式、完成程度、正式接入與驗證證據、缺口及觀察日期；舊資料本輪補建的識別須明標。
7. **交付與完成判斷。**方案交付與實作完成分開回報；每項能力採用程度依證據記為已採用、部分採用、未採用、已排除或不確定。已採用須有正式實作、接入及對應行為驗證，部分採用須列已完成／剩餘項。未採用須有明確未落地證據或足夠的有界查核；已排除須有決策理由，證據不足或衝突用不確定。既有正式行為已滿足需求時不強迫新增程式，並區分能力滿足與實驗來源關係。

# Examples
- 正例：E001 驗證解碼、重試與示範介面；正式需求只需解碼，沿用既有重試，只調整解碼邏輯及邊界測試，記錄其接入證據，排除示範入口。
- 反例：E001 標為成功，便把整個目錄複製進正式來源，將所有能力記成已採用。
- 需處理依賴、重寫、權限或舊資料時，讀 [examples.md](examples.md)。

# Outputs
- 能力／決策層級的採用方案與來源、範圍、依賴、理由及證據限制。
- 已有授權時的 bounded implementation、實際接入與驗證／審查結果；未做事項清楚保留。
- 獨立採用紀錄或相同結構的待寫入內容，不改變驗證四狀態與驗證任務完成判斷。

# Validation
## Required Checks
- 所選能力對應正式需求及適用證據；必要依賴有交代，未整套搬入無關實驗構件。
- 方案、已做實作與待辦分開；沒有超出原授權或自行重開鎖定決策。
- 正式來源及接入按實際用途確認；完成程度與行為證據一致。
- 來源版本、重寫／重用方式及歷史可追溯；採用紀錄與實驗結果分離。

## Quality Checks (best effort)
- 採用範圍足夠小且可審查，指出解除每項缺口所需的下一個證據。

## On Soft Fail
可恢復的紀錄或證據缺口標 `SOFT FAIL`／`INCOMPLETE`，保留安全方案與已完成部分。若缺口使採用結論或正式實作產生誤導，標 `BLOCKED` 並停止依賴該缺口的動作；不抹去其他已取得的證據。

# Failure Handling
## Missing Context
先查原任務、來源與既有程式；無法確定需求、必要依賴或證據適用性時，列出精確缺項。可獨立完成的方案繼續，受影響部分不冒充已可採用。

## Ambiguous Requirement
能從需求、規範與來源解決的技術選擇主動提出有依據方案；只有未解的重大需求／授權歧義才詢問。非關鍵假設明示，不冒充使用者需求。

## Execution Limitation
寫入、工具或環境不足時，交付具體方案、實際完成部分及缺少的驗證。指令未執行或失敗不能捏造成通過；必要行為驗證不足不能標已採用。

# Workflow State Contract
若參與既有 multi-agent handoff，回報 `current_step`、`next_step`、`status: IN_PROGRESS|COMPLETE|INCOMPLETE|BLOCKED`，並明列方案／實作交付終點及證據。這是本輪處理狀態，不替代採用程度或實驗狀態，也不建立新 workflow。

# Boundaries
- 不把驗證成功、驗證任務完成、程式存在或計畫核准當作實作完成。
- 不新增必經 phase、approval、runtime orchestration 或自動發布；實作與審查沿原流程。
- 不藉採用取得覆寫歷史、修改不相關來源、merge、tag 或發布權限。
- 不要求修改 feasibility-validation 或實驗 README 才能使用本 skill；不依賴另一個 skill 的隱藏規則。
