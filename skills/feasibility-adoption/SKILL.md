# Purpose
選擇性採用有證據支持、符合正式需求的驗證成果，留下能力／決策到正式實作與實際消費的對應。

# Trigger / When to use
- 使用：已有可行性證據，需要決定哪些能力進入正式實作，或執行已授權的選擇性採用。
- 排除：重新設計可行性實驗、無驗證成果的一般功能實作、全專案採用盤點、發布或改寫鎖定決策。
- 可從文件／原始碼驗證結論開始，不要求實驗目錄或成功標記。

# Inputs
- 目標需求、原任務授權、已鎖定決策及目標專案規範。
- 選定驗證的問題、結論、來源版本、條件、限制與證據。實驗程式可作為素材。
- 可得正式來源、實際消費端、既有能力及採用／決策紀錄。

# Process
1. **定位交付範圍與授權。**唯讀確認本輪承諾的是契約、單一能力、元件、協調行為或完整產品整合，列出該範圍須交付的組合與行為。依語言、框架、實際用途與專案規範定位正式來源。先查需求、決策與授權，只有仍會實質改變需求、風險或授權的歧義才詢問，暫停依賴該決定的動作。
2. **拆出必要能力。**以能力／決策辨識支持目標需求的成果，分開事實、推論與缺口。列出重用、抽取調整、重寫或排除的理由，僅選正式需求所需的成果。模擬及有限輸入的證據只適用於查驗過的條件。失敗或無法判定時，保留原結論。若有證據支持另一選擇，列明依據與限制。
3. **確認必要依賴。**將所選能力的必要依賴對應至既有正式能力、本輪必要實作或待解缺口。等效既有能力可滿足依賴，其實驗來源關係須另有證據。若必要正式依賴未解，保留方案並暫停依賴該缺口的實作。驗收可用替身提供範圍外依賴，受驗能力本身須為真實正式實作，證據限於該組合實際查驗的行為。
4. **形成採用方案與接入位置。**列出正式交付、驗收支援各自的用途、接入位置及預定查驗。必要邏輯與有價值的測試可重用、調整或重寫，保留正式介面、錯誤處理、生命週期及適用條件。測試、Preview、runner 或受控 host 可直接消費正式能力。驗收用 harness、fixture、診斷、模擬或示範入口只在必要時留於獲准的驗收位置。另查來源的寫入權，依目標專案現行規則區分凍結驗證、持續維護工具或本輪新增組裝。凍結來源需要改接時，選用獲准的驗收位置並保留原版本的重現線索。持續維護工具可在既有授權內作必要調整。以 Git 歷史追溯來源，以現行規則及授權判斷寫入權。Plan 結案本身不會凍結曾涉及的正式來源。
5. **依原授權實現及查驗。**已有實作授權時沿專案原流程完成範圍內實作、驗證與審查，沿用同範圍授權。僅有驗證授權或模式限制寫入時，交付可審查的採用方案。影響鎖定決策時走原變更流程。明確限制或重大衝突仍待解時，提出最小替代差異及所需決定，繼續獨立可完成的工作。承諾可執行行為時，由具體消費端實際執行正式實作並取得對應結果。純契約以具體消費端的相容性或遵循證據驗收。空方法、未執行的測試或 Preview 宣告都留下證據缺口。
6. **獨立記錄。**沿用專案既有採用紀錄落點，沒有則用 `docs/feasibility-adoption.md`。依寫入權限用 [模板](templates/adoption-record.md) 新增／更新，保留歷次依據與實驗 README。無法寫入時交付相同結構的內容及限制。記錄來源、交付範圍、依賴、正式實作、驗收入口、受測版本、替身、結果及觀察日期。產品接入另記本輪要求、實際位置、證據及缺口。舊紀錄按原內容讀取，缺少新欄位本身不構成未採用證據，本輪補建的識別須明標。
7. **交付與完成判斷。**分別回報方案交付與實作完成。已採用須有本輪契約對應的正式實作、具體消費及適用驗收證據。產品整合在範圍外時，按該能力的證據驗收。產品整合在範圍內時，受控驗收只支持實際查驗的範圍，另須產品端的實際接入證據。已確認部分落地但仍有必要接入或驗收缺口時，記部分採用並列完成與剩餘項。未採用須有明確未落地證據或足夠的有界查核，已排除須有決策理由，證據不足或衝突而無法判定時記不確定。既有正式行為已滿足時可沿用，另記其與實驗來源的關係。

- 反例：E001 標為成功，便把整個目錄複製進正式來源，將所有能力記成已採用。

# Outputs
- 能力／決策層級的採用方案及來源、交付範圍、依賴、理由與證據限制。
- 已有授權時的範圍內實作、實際消費、驗證與審查結果，列出待完成事項。
- 獨立採用紀錄或同結構的待寫入內容，沿用驗證四狀態與驗證任務完成判斷。

# Validation
## Required Checks
- 所選能力對應正式需求及適用證據，完成本輪必要組合，交代依賴及排除理由。
- 方案、已做實作與待辦清楚，寫入範圍符合原授權、來源規則與鎖定決策。
- 核對具體消費端、受測正式版本與對應結果。查驗替身用途及適用界線，按本輪承諾核對產品端證據。
- 來源版本、採用方式及歷史可追溯，採用判定依實際證據獨立記錄。

## Quality Checks (best effort)
- 採用範圍足夠小且可審查，指出解除每項缺口所需的下一個證據。

## On Soft Fail
可恢復的紀錄或證據缺口標 `SOFT FAIL`／`INCOMPLETE`，保留安全方案與已完成部分。若缺口使採用結論或正式實作產生誤導，標 `BLOCKED` 並停止依賴該缺口的動作，保留已取得的證據。

# Failure Handling
## Missing Context
先查原任務、來源與既有程式。無法確定需求、必要依賴或證據適用性時，列出精確缺項，繼續可獨立完成的部分。

## Ambiguous Requirement
能從需求、規範與來源解決的技術選擇主動提出有依據方案，明示非關鍵假設。只有未解的重大需求／授權歧義才詢問。

## Execution Limitation
寫入、工具或環境不足時，交付具體方案、實際完成部分與驗證缺口。記錄指令未執行或失敗的事實，按已取得的證據判斷採用程度。

# Workflow State Contract
若參與既有 multi-agent handoff，回報 `current_step`、`next_step`、`status: IN_PROGRESS|COMPLETE|INCOMPLETE|BLOCKED`，並明列方案／實作交付終點及證據。這是本輪處理狀態，不替代採用程度或實驗狀態，也不建立新 workflow。

# Boundaries
- 完成判定依實際接入及對應證據，驗證成功、驗證任務完成、程式存在或計畫核准均不足以單獨支持。
- 實作與審查沿原流程，不新增必經 phase、approval、runtime orchestration 或自動發布。
- 採用授權不涵蓋覆寫歷史、修改不相關來源、merge、tag 或發布。
- 可獨立使用本 skill，無須修改 feasibility-validation 或實驗 README。
